# Architecture rules
- Admin access checks depend on account ID and session token, not User object identity; same-account token rechecks keep content mounted with actions disabled, while account changes, stale responses and errors fail closed through the existing server gate.
- Supplier-detail top-up windows load the full protected supplier list with configured fees, placing the current supplier first so records can target any supplier without changing accounting RPCs.
- Admin reference searches use the protected targeted order-search helper independently of recent/date-filtered browsing caches, so historical orders remain findable without loading the whole table or weakening access controls.
- Global maintenance uses agent_plan.maintenance and atomically stored transition announcements via the master/AAL2 settings RPC; main/store bells merge those notices and storefront gates resolve their own identity. Browser safeguards do not replace external server enforcement; maintenance emails go through the maintenance-email outbox (unique per notice+address, Resend idempotency keys), so retries never duplicate.
- Kora Finance uses its complete live available plus pending GHS balance instead of book kora_held, never both; external cash records preserve history but are not re-deducted from provider balances. Kora-specific refund semantics remain separate from Paystack.
- Current and legacy Finance pages reuse PaymentGatewayCard for provider selection, preserving the existing master-admin switch and server checks without duplicating payment settings logic.
- Public catalogue loading merges network pauses into product availability and fails closed when network availability is unknown, so all catalogue consumers block purchases consistently without changing server purchase rules.
- Delivery-ahead profit is display-only: simulate healthy supplier-accepted queued delivery by releasing delivery and pending-fee liabilities, creating agent/parent margin debts, and deducting supplier costs only for ledger-fallback assets; never alter main profit or money records.
- Supplier credit markers use admin-only audit logs and an AAL2-checked phase1 RPC, bound to the exact supplier attempt; never store evidence in customer-readable order events or change status/financial records, so recording recovery cannot issue a refund.
- Admin refund entry points, including Orders received row actions, reuse RefundDialog and a server-verified quote through refund-policy; refund-order (source mirrored in supabase/functions/refund-order, deployed externally) is the money authority: it takes the order's send lock for every refund, re-verifies Paystack's actual fee for MTN-verification fee-deducted refunds, and records refundAmount in the refund.completed event so finance_clear_paystack_refund books the retained fee once.
- Finance's pending-fee estimate is a separate pure display calculation on unscheduled money only; never change the primary asset calculation or re-deduct scheduled deductions/refunds, so the comparison cannot affect financial records.
- The Finance page (/admin/finance, rebuilt; old pages hidden at /admin/finance-old and /admin/new-finance) computes profit as bank (existing pot ledger) + Paystack API held money (scheduled net + pending transfers − Paystack refunds not fully deducted) + supplier reported balances − all liabilities − partner funding, showing no totals if any Paystack part is missing; bank moves only via existing top-up, master adjust (spend/withdraw), partner capital and payout RPCs, and wallet refunds never touch the bank.
- The New Finance Page takes Paystack's held money from Paystack's API (pending transfers + scheduled payout net, GHS only, admin-protected read-only lookup) and shows no totals when that reading is incomplete, so profit never silently falls back to our own ledger estimate.
- Net-assets finance is a separate admin comparison route using protected existing asset/liability balances and only the partner funding account for capital, matching the original Finance page rather than adding carried-in accounting funds; recorded spending uses the existing master spend RPC so history is retained and cash is deducted only once.
- Promotion admin sections use separate routes under a standalone ADMIN_GROUPS dropdown and share the existing settings/report services, keeping each page focused without changing promotion or payment rules.
- Promotion link pricing runs on the main shop (?promo marks a capability-bound device visit); eligibility (one use per device visit, recipient number and account) is decided only by phase1 RPCs — accounts via promotion_prepare_order, guests via short-lived claim tokens priced through the existing campaign_price_for hook — so no edge-function redeploy is needed and ineligible shoppers fall back to normal prices instead of being blocked.
- Promotion analytics use capability-bound first-touch visits, an auth-row creation trigger for actual signups, and redemption/payment records for conversions; report visitor cohorts in Africa/Accra through admin-only RPCs to avoid counting sign-ins or client claims as purchases.
- Unpaid cancellation uses a row-locked, ownership/MFA-checked phase1 RPC; guest management requires a private device capability or checkout email plus order reference, and late payments on cancelled orders stay closed for manual reconciliation to prevent duplicate delivery.
- Returning checkout uses the shared verified unpaid-order recovery view only after the shopper enters the same recipient number; opening the shop or buying for another number is not blocked by an older unpaid order. Cancelling clears only that reference's device hints and returns to bundle selection, never silently deleting orders or changing paid orders.
- Parent sub-agent controls use an ownership-checked RPC and parent pause marker; administrator status decisions clear that marker so parents cannot override suspensions.
- Apply application SQL and deploy functions to the active external database's phase1 schema, never the unused managed backend, because production data lives externally.
- Order SMS uses a private database outbox with unique order/kind keys and atomic claims to cover all payment and delivery paths without changing fulfillment.
- SMS remains disabled until an internal-only test passes and sending is activated explicitly; quarantine provider-ambiguous sends rather than automatically retrying them to avoid duplicate charges.
- Keep SMS eligibility and templates in a pure shared module with concrete status and segment-limit tests.- The per-store 'send visitors to main site' switch is checked by its own public RPC before the store renders, independent of plan status, so it also covers lapsed stores.
- Paystack refunds on payments received on/after the newest scheduled payout date are already removed from Paystack's pending_transfers, so the Finance page skips them in 'refund not yet deducted' (matched via orders.refund_reference → paid_at; unknown dates still subtract).
- DataSika buys by its own product_id, resolved live from /api-catalog by network + GB at purchase time (mappings keep GB), and no-answer resends reuse the same Idempotency-Key so DataSika replays the original order instead of charging twice.
- DataSika purchase and admin recheck retain paid failure receipts and wait for confirmed supplier refunds; request_in_progress and malformed success replies are ambiguous so fallback cannot create a duplicate delivery.
- Partner programme: ?p=CODE links attach main-shop orders via the owner-checked phase1.partner_attach_order RPC; a status trigger credits fixed per-product rates only on delivery (voids unpaid on refund) and posts to owed_to_partners, so Finance shows the debt automatically and payouts (bank down, debt down) never change profit twice.
- Promo-link tracking: only browsers holding a promo touch report steps (phase1.promotion_event, capability-bound, never raises); orders, payments, deliveries and top-ups are read from real records and tied to a visit by promotion_order_links()/promotion_deposit_links(), never trusted from the browser. Tracking has no time limit; the promotion price keeps its own 30-day rule. Admin page: /admin/promotions/tracking (admin_promo_tracking, admin_promo_visitor; Ghana days, activity inside the chosen days).
- Phones use an app-style bottom tab bar (MobileTabBar) instead of a three-line menu: PublicNav for customers and guests (below lg), AgentShell for agents (below sm). The admin panel keeps its menu. Pages end with TabBarSpace so nothing hides behind the bar.
- The site is light only: dark mode and its switch were removed (10 Nov 2026); src/store/theme.tsx and index.html always set `light`. Do not add a theme switch or dark-only styling.
- Touch devices get no live blur (backdrop-filter is switched off in index.css); bars that relied on it carry `touch-solid`. Do not add backdrop blur, blurred drifting shapes or endless animations to pages customers scroll.
- The Android app (android-app/, Capacitor, app ID com.datayego.app) is only a shell that opens https://datayego.com, so site publishes reach it at once; it is built by .github/workflows/android-app.yml. Inside it the page runs under the status bar: `--sat` (safe-area top) pads the body, sticky bars use `top: var(--sat)`, full-screen drawers carry `app-safe-top`. Keep these when adding sticky headers or full-screen overlays.
- Agent payouts are marked paid from the bank or from Kora (agent_payouts.paid_from/paid_charge, set by admin_set_agent_payout_source before admin_settle_agent_payout); a Kora payout posts to book kora_held and kora_fees only, never the bank, and Finance reads Kora's live balance so nothing is deducted twice.
- "Get the app": AppBanner (top of the public site on phones) and /app (GetApp) offer the Android APK or, on iPhone, Add to Home Screen. The offer never shows inside the app, in standalone mode, or when Chrome reports com.datayego.app installed (manifest related_applications + the app's asset_statements). The APK and public/app/version.json are written by the Android build, never by hand; the page shows only real facts (size, version), never ratings or download counts. The app is signed with the key in the ANDROID_SIGNING GitHub secret; changing that key means every installed copy must be removed before updating.
- App counters: phase1.app_track (anonymous device ID, once a day per kind) records Download taps on /app, iPhone guide views and app opens (trackAppOpen in main.tsx, only when running as the app); admin_app_stats feeds the "DataYego app" card on the admin Overview. A download tap is not proof of an install; "phones with the app" (app opens) is the reliable figure.
- Phone notifications: DB queues in phase1.push_outbox (triggers on orders/announcements, push_enqueue respects site_settings push_notifications); edge function push-send delivers via FCM (secret FIREBASE_SERVICE_ACCOUNT). Client: src/lib/push.ts (Capacitor bridge only, no npm deps). Admin switches: PushCard on /admin/announcements. Never send from the client or bypass push_enqueue. Since 13 Nov 2026 it also covers DY Services orders (kinds service_delivered / service_refunded, trigger on service_orders, one switch "services") and agent approval (kind agent_approved, trigger on agent_applications); these go to the account's phones or the phone that placed the order, and a PIN is never put in a notification.
- Follow-ups (automatic reminders): phase1.follow_up_messages/sends/optouts, follow_up_due() decides who is due, follow_up_claim() enforces switch, 9am-7pm Accra, daily cap and writes the app notification; edge function follow-up-run only sends email. Offer = invite-only campaign slug "welcome" (campaigns.invite_only, follow_up_invited). Admin: /admin/follow-ups. Agents and admins are never followed up.
- Google tag: src/lib/googleTag.ts (GTM-MLN34QZK), loaded via TikTokConsent apply(); never in /admin, never in consent countries; purchase event pushed to dataLayer next to trackMetaPayment (not for agent stores, not for top-ups).
- Invite offer: an invited friend's first order gets ONE bundle at a set price (site_settings invite_offer; price_for_user / invite_offer_eligible / invite_offer() / my_friend_price returns {prices}). The old agent-price-on-everything rule is retired (friend_price_eligible returns false). Share/copy text comes from inviteMessage() in src/lib/referrals.ts. Referral rewards are not held when the payer is unknown (wallet or Kora).
- Payment guard: phase1.payment_guard_run() every 5 min (cron payment-guard). 10+ failed attempts from 6+ payers since a gateway's last success -> push kind "alert" to admins (hourly at most); auto-switches Kora -> Paystack only, never to Kora.
- DY Services (result checkers; AFA later): own tables phase1.service_* (never the orders table). PINs sold once (service_hold reserves, service_fulfil sells; paid-with-no-stock waits and delivers when stock is added). Wallet: RPC service_buy_wallet. Paystack: edge function service-pay (self-contained, shares no code with data checkout) + trigger on payment_events for references starting SVPAY-. Finance accounts stock_services/services_owed/service_revenue/cost_of_services; Finance V2 counts stock_services as something we own. Pages: /services, /services/order/:token, /admin/services.
- MTN AFA registration (DY Services, product kind "afa", code afa-mtn): a paid form, not a PIN. Paid order -> status 'processing' + one row in phase1.service_registrations; service-pay sends it once to OtessData (POST /afa/register, Idempotency-Key = order reference; secret OTESSDATA_API_KEY, without it nothing is sent and admins register by hand). It becomes 'delivered' only through service_registration_done, with the cost OtessData says it charged, taken from float_otessdata (supplier row otessdata is 'paused' so it is never offered for data orders). Unclear answers are never retried automatically. One number can be in progress or registered only once (service_afa_taken). Buyers never get the Ghana Card back from any RPC; form checks live in src/lib/afa.ts and phase1.service_afa_details.
- DY Services for agents: phase1.agent_service_prices (per agent: price, enabled; never below service_products.agent_price). Store orders pass the store slug (service_catalog(p_store), service_order_new p_store) and carry agent_id + agent_margin, credited on delivery by the existing service code; an agent buying for themselves passes p_as_agent (agent price, wallet only, no margin). No parent-agent share on services. Store pages: /services inside the store (StoreServices reuses pages/Services with a `store` prop; no DataYego wording there); dashboard: /agent/services (agent_services, agent_service_set).
- Kora refunds (13 Nov 2026): refund-order refunds a Kora-paid order through Kora's Refunds API, always the full amount paid (no fee deduction) and never under GHS 10 (smaller ones are sent by hand and recorded as manual). The refund reference is RF-<order reference> (-2..-4 after a failed attempt); Kora is asked about that reference before and after the request, so a retry finds an accepted refund instead of sending a second one. The order is marked refunded only on Kora's "processing"/"success"; Kora's signed refund webhook arrives at the same refund-order URL and records refund.kora_confirmed / refund.kora_failed (+ admin_alert). finance_clear_kora_refund books it against kora_held (records only: Finance reads Kora live).
- refund-order without an admin session only accepts the database's own out-of-stock nudge, proved by the internal cron secret header (nudge_auto_refund sends it). Never add another unauthenticated caller.
- check-mtn-number "submit" is a real purchase request to the supplier: it is made only after the supplier has just answered "not_approved" (never after a failed lookup), and inside the daily allowance from phase1.number_submit_allow (100 per visitor hash, 1,000 overall, Ghana day; signed-in admins exempt). Outcomes try_later and limit_reached mean nothing was submitted; the site must not mark those numbers as submitted (submitLanded in src/lib/mtnCheck.ts).
- Every CSV export goes through csvText/csvCell in src/lib/csv.ts, which stops customer-typed text being run as a spreadsheet formula. Do not hand-build CSV lines.
- DY Services are on in every active store by default (13 Nov 2026): a store with no row in agent_service_prices sells each active service at the customer price (agent earns customer price minus agent price); a row is the agent's own price or "off". service_catalog(p_store), service_order_new and agent_services all read it that way. Do not require a row to sell.
- The AFA form is one component (components/services/AfaForm): on /services/afa and in stores it is the page itself (three numbered steps, each in a card, then payment), and AfaSheet wraps the same form in a pop-up for the agent dashboard. Checks run top to bottom in form order (lib/afa.ts) and again in phase1.service_afa_details; "Town or area" may be 2 characters (Wa, Ho).
- Agent stores on phones (below md) use the same bottom bar as the main site (MobileTabBar with class st-tabbar): Home, Buy data, Services (when the store sells any), Track, More. "More" opens the existing menu drawer; the header menu button only shows from md up. Templates restyle the bar in components/store/templates.css; the store's floating WhatsApp and chat buttons sit above it.
- Service prices are shown the way the data checkout shows them: our price on its own line, the payment fee on its own line, then the total (components/services/PriceBreakdown, used by the AFA form and the checker buy sheet). Never show only price-plus-fee as "You pay": buyers read it as our price.
- Admin menu: DY Services is its own group (not under Announcements), one page per job: Overview (/admin/services), Result checkers (/checkers), AFA registrations (/afa), Orders & refunds (/orders), Text messages (/sms). All five are the one AdminServices component reading `:section`; new service admin screens go in this group. pageForPath matches a group's first page (`end`) by its exact address.
- DY Services texts (13 Nov 2026): the wording lives in supabase/functions/service-pay/texts.ts (tested by src/lib/serviceTexts.test.ts). Every PIN goes in the text as "S/N … PIN …", five to a text; above 50 checkers one text points to the email or the order page. Never put the exam name (WASSCE, WAEC, BECE), "Results Checker", the product name or a website in a text: the network accepts such texts and never delivers them. The results website (service_products.use_at) is shown on the order page and in the email only. Texts to the same phone go out 5 seconds apart (sendSpaced in service-pay): sent in the same second, one to three of every five never arrived in testing. Never send several texts to one phone back to back.
- Text delivery (13 Nov 2026): "sent" only means the SMS provider took a text; about a third of accepted texts never reached the phone in testing. Every text service-pay sends is recorded in phase1.service_sms (who, sender, the provider's job id; never the text, it can carry a PIN) and service-pay asks the provider what the network did (service_sms_due decides when, service_sms_report records it; delivery.ts reads the reply). Admin -> DY Services -> Text messages lists each text as Delivered / Sent, not delivered / waiting (lib/smsDelivery.ts). Judge a wording or a sender by these reports, not by "sent".
- Order profit (the Orders page "Delivered" tile and the Overview "Order profit" stat) comes from phase1.admin_orders_profit(p_from, p_to, p_source): per delivered order, amount − supplier cost − agent earnings − parent share − partner commission + the checkout fee actually collected − the charge Paystack or Kora actually took (read from the payment's own record, never a percentage). It is read-only and separate from Finance; do not go back to finance_overview's order_profit for these two figures (it leaves out the gateway's cut and the ":parent" share). src/lib/ordersProfit.ts lists the parts shown under the tiles.
- Start-up screen (13 Nov 2026): index.html is also what the host sends for every address without its own file (agent stores, dashboards, order pages), and it carries the pre-built DataYego home page. A script in <head> decides before anything is drawn whether that pre-built page belongs to the address (main site only, exact path, read from `<html data-prerendered>` written at build time); if not it adds `html.yg-boot`, which hides the markup and shows a plain loading screen (#yg-boot) until main.tsx sees the app's first screen. On stores the screen shows the store's own name, logo and colour remembered from the last visit (src/lib/storeBrand.ts; the body script reads the same keys). StoreSplash is the same screen drawn by the app while a store is looked up; never use a blank or dark placeholder there. Keep the main-site host list in index.html in step with src/lib/storeHost.ts (a test checks it), and never hydrate pre-built markup on a store host.
- A checker voucher (serial) may be in stock under one product only: admin_service_add_stock refuses a serial that already exists under any product (voided rows under another product aside) and reports it as "already in stock". Never relax this to a per-product check; the same PIN on sale twice is a duplicate sale.
- An "agents" announcement reaches paid agents only (13 Nov 2026): in the bell (my_announcements) and by email (agent-announce-email) a main agent who has paid for a plan (paid_until set; active or run out); by phone notification an active main agent. Approved applicants who never paid count as customers, and sub-agents are never included (they only know their parent's store). Keep the three in step.
- Emailing an announcement to customers without the admin panel (13 Nov 2026): edge function announce-send (internal secret only, self-contained) sends 60 at a time and the database calls it again until none are left (phase1.announcement_email_outbox + announcement_email_queue/claim/done/continue; one row per announcement + address, Resend idempotency key per row). The database decides who gets it: never sub-agents, never an address in follow_up_optouts, and with skipAgents never paid agents. Agents-only announcements still go through agent-announce-email. A notice for people buying in agent stores is a row in store_announcements per store, in the store's own voice: no DataYego name and no prices.
- Services awareness (13 Nov 2026): components/services/ServicesPopup tells visitors about result checkers and AFA, once per device per site (main site, or each agent store, where it uses the store's name and its own prices and no DataYego wording), only on the home page and the bundle list, never over the buy sheet or for a promo-link visit, until POPUP_UNTIL (27 Nov 2026); a "New" tag sits on the Services button until the person opens Services or NEW_TAG_UNTIL. Rules and memory live in lib/servicesNews.ts. A visit never gets two pop-ups: AgentPopup and StorePopup stand down through that file (notePopupShown / servicesPopupOwed); any new pop-up must do the same. On the main site a pop-up is mounted beside FloatingSupport, outside the page column, or the floating help button covers it.
- A supabase-js call (`.rpc(...)`, `.from(...)...`) is a thenable with .then() only: it has no .catch() or .finally(), and calling one throws on the spot (13 Nov 2026: that left the admin Overview on dashes for hours). Give a call a fallback with settled() from lib/settled.ts, type such calls as PromiseLike, and make test stand-ins thenable-only (see pages/Admin.test.tsx), never plain Promises. On the Overview each part loads on its own; the profit figure never holds back the counts.
- Adverts (13 Nov 2026): every paid advert has its own link and its own results under Admin -> Promotions -> Adverts (components/admin/PromoAdverts, lib/promoAdverts.ts). phase1.promotion_adverts names an advert by the tag on its link (the campaign tag, case ignored; or the source, for an advert known by its source); phase1.promotion_advert_of() is the one place that match lives, and a visitor stays with the first advert that brought them. admin_promo_tracking(from, to, advert) returns every advert with its own figures ("adverts"), tagged links nobody has named yet ("unnamed") and, when an advert is passed, the whole report for that advert alone. Adverts are added, renamed and costed through admin_promo_advert_save; a tag never changes once made, so links already handed out keep counting. Checker and AFA sales count for an advert through promotion_event kind 'service_order' (sent by lib/services.ts for main-site orders only) and promotion_service_links(); a service order placed in an agent's store is never counted for our advert.
- Queued texts (13 Nov 2026): a row picked from sms_queue or service_outbox is held for 4 minutes (claimed_until) so two overlapping runs can never send the same text or PIN email twice; the run releases it when it records the result (sms_queue_done / service_outbox_done). Never go back to picking rows without the hold. Approval texts are spaced: sms_queue.not_before gives each one the next free slot, 5 minutes after the one before (twelve approvals sent within 20 seconds had three delivered), and at most 3 queued texts leave in one run. Anything new that queues texts for many people must set not_before the same way, never send a burst.
- Store customers never see our name (13 Nov 2026): an agent's customers must not meet "DataYego" or "Yiego" in anything we send or show them. The order email for a store order is sent by edge function store-order-email (self-contained), in the store's name, from `<Store name> <stores@datayego.com>`, with links to the store's own address and "<Store name> · payments secured by Paystack" at the foot. The database queues it: trigger zz_store_order_email_trg on orders writes store_order_email_outbox and the order's 'notification.email_sent' / 'notification.verifying_email_sent' event at once, which is what makes the payment functions skip their own email, so no payment function had to be redeployed. Never remove that trigger without redeploying every payment function first. Anywhere a store shows who secures the payment it says Paystack, never us (StoreShell footer). The Paystack checkout name and the slug.datayego.com address are the owner's accepted exceptions. The refund email goes the same way: trigger zz_store_refund_email_trg on order_events (refund.completed) queues kind 'refunded' with what went back, why and how, and writes 'notification.refund_email_sent' at once so refund-order skips its own; the reason typed in the refund box is shown to the customer. A kind store-order-email does not know is refused, never guessed. Still carrying our name to store customers: replies, which go to support@yiego.shop.

- The shop's band (14 Nov 2026): components/shop/ShopBand is the top of /shop. Signed in: the greeting, the wallet (components/shop/Purse: balance, show or hide, Add money) and the latest delivery, in one band; never two big cards stacked. Not signed in: the page's name and the latest delivery. The delivery (DeliveryBoard, DeliveryNow in components/shop/LatestDelivery; rules in lib/latestDelivery.ts) is one real order from phase1.public_latest_delivery() (public, read-only, one per network; orders MTN held to verify, or sent to the wrong network, are left out): size, number shown as 055*****47, the minute it was paid and the minute it landed, how long that took, then what the network is doing right now in the catalogue's own words.
